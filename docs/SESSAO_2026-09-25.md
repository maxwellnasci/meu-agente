## 2. Achado crítico de arquitetura — `phoneNumberId` não é SecretRef

### O problema

No OpenClaw, os campos de `channels.whatsapp-cloud` **não se comportam do
mesmo jeito** dentro do `openclaw.json`:

| Campo | Aceita `${VAR}`? | Por quê |
| --- | --- | --- |
| `accessToken` | ✅ sim | passa por `resolveConfiguredSecretInputString()` (`src/config/types.secrets.ts`, `ENV_SECRET_TEMPLATE_RE`) |
| `appSecret` | ✅ sim | idem |
| `verifyToken` | ✅ sim | idem |
| `phoneNumberId` | ❌ **não** | lido cru em `extensions/whatsapp-cloud/src/accounts.ts:82` — `String(merged.phoneNumberId ?? "").trim()` |

Um `"${WHATSAPP_CLOUD_PHONE_NUMBER_ID}"` no `phoneNumberId` **não é
resolvido**: vira a string literal `${WHATSAPP_CLOUD_PHONE_NUMBER_ID}`.

### A falha silenciosa é dupla

1. **Envio quebrado** — a URL do Graph é montada com o ID literal inválido,
   e a chamada à Meta falha.
2. **Recebimento quebrado, sem retry** — em
   `extensions/whatsapp-cloud/src/webhook.ts:176-180`, quando o
   `phone_number_id` do payload não bate com o do account, o gateway
   registra `WhatsApp Cloud webhook rejected mismatched phone_number_id` e
   responde **`respondPlain(res, 200)`**. Ou seja: a Meta recebe ACK, **não
   reenvia**, e a mensagem é descartada. Nada estoura, nada retenta — o
   agente simplesmente não responde.

O agravante é que `isWhatsAppCloudAccountConfigured()` (`accounts.ts:92`)
só checa se o campo é **não-vazio** — a string literal passa nessa
validação. O deploy sobe "saudável" e morre no primeiro turno real.

### Solução arquitetural adotada

- O `openclaw.json.template` traz o marcador literal
  **`__WHATSAPP_CLOUD_PHONE_NUMBER_ID__`** no lugar do número.
- O `bootstrap.sh` substitui esse marcador pelo valor de
  `WHATSAPP_CLOUD_PHONE_NUMBER_ID` lido do `.env` — no 1º run (arquivo
  novo) **e** nos runs seguintes (arquivo já existente que ainda contém o
  marcador). Isso cobre o fluxo real de VPS virgem, em que o operador roda
  o script *antes* de ter os segredos em mãos.
- Se o marcador sobreviver, o script **avisa antes de subir a stack**, em
  vez de deixar a falha silenciosa acontecer em produção.
- Dois guard-rails antes da substituição: recusa o número de exemplo da
  documentação (`123456789012345`) e recusa valor que não seja só dígitos
  (evita que `/`, `&` ou `\` de um `.env` editado à mão escapem para o
  `sed` e corrompam o JSON).

> Nota relacionada, documentada no `.env.example`: o template sobe com
> `"dmPolicy": "open"` e `"allowFrom": ["*"]` de propósito, para não travar
> o handshake e o onboarding. O default do próprio código é `allowlist`
> (`accounts.ts:88`) — em produção com número restrito, o operador deve
> voltar para `allowlist` e listar os contatos autorizados.
