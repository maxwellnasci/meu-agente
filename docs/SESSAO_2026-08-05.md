# Sessão 2026-08-05 — P0.2: sandbox real ativado em produção (Contabo)

## Contexto

Item 2 da "Sequência de segurança pendente" registrada em
`docs/PROXIMOS_PASSOS.md` em 2026-08-04, logo após a remoção do
`docker.sock` do gateway (P0.1) — feita porque o mount sem sandbox real
era uma rota RCE→root. O objetivo desta sessão era religar o
isolamento, desta vez com sandbox de verdade (`sandbox.mode: "all"` +
limites de recursos), não do jeito antigo sem proteção.

## 1. Investigação (read-only)

- **`openclaw-sandbox:bookworm-slim` não existia no Contabo.** É uma
  imagem separada da `openclaw:local` do gateway, usada pelos
  containers-filho `openclaw-sbx-*`. Confirmado no código-fonte
  (`src/agents/sandbox/config.ts`) e na doc oficial
  (`docs/gateway/sandboxing.md` do upstream).
- **`OPENCLAW_INSTALL_DOCKER_CLI`** confirmado no `Dockerfile` real:
  quando setado, instala `ca-certificates curl gnupg`, adiciona o repo
  APT oficial do Docker com verificação de fingerprint GPG pinado
  (`9DC858229FC7DD38854AE2D88D81803C0EBFCD88`) e instala
  `docker-ce-cli` + `docker-compose-plugin` (só o CLI, não o daemon). A
  imagem rodando em produção tinha sido construída com essa flag vazia.
- **Bloqueador real: sem Dockerfile em `/root/openclaw` no Contabo.**
  O `docker-compose.yml` (e os 4 backups anteriores) usam `build: .`,
  mas não existe Dockerfile ali nem em lugar nenhum do servidor — a
  imagem `openclaw:local` atual foi transferida pronta do Kali durante
  a migração original (2026-07-29), nunca construída no próprio
  Contabo. Um `docker compose build` ali falharia hoje.
- **Docs oficiais confirmam valores de referência**: exemplo em
  `docs/gateway/config-agents.md` do upstream usa `pidsLimit: 256` e
  `memory: "1g"` (+ `memorySwap: "2g"`, `cpus: 1`). `pidsLimit: 256` da
  proposta batia exato; `memory: "512m"` é mais conservador que o
  exemplo (1g).
- **GID do grupo `docker` diverge entre as máquinas.** Kali usa 124
  (hardcoded no `docker-compose.yml` local, não versionado). No
  Contabo: `docker:x:988:` — GID diferente, confirmado via
  `getent group docker`.
- **Confirmado**: `sandbox.mode` estava `"off"` no `openclaw.json` de
  produção antes desta sessão; o mount do `docker.sock` estava mesmo
  ausente do `docker-compose.yml` (só um comentário residual mencionando
  ele), consistente com a remediação P0.1 de 2026-08-04.

## 2. Decisão de estratégia de build

Duas opções levantadas: (a) buildar no Kali (onde o Dockerfile já
existe, branch `production-local-fixes`) e transferir a imagem pronta
via `docker save`/`load`, ou (b) sincronizar o código-fonte pro Contabo
e buildar lá. Escolhida a opção (a) — mesmo método já usado na
migração original de 2026-07-29, evita manter um checkout de
código-fonte completo no servidor de produção.

## 3. Build e transferência

```bash
# No Kali:
cd openclaw/
docker build --build-arg OPENCLAW_INSTALL_DOCKER_CLI=1 -t openclaw:local-sandboxed .
docker build -t openclaw-sandbox:bookworm-slim -f scripts/docker/sandbox/Dockerfile scripts/docker/sandbox/
```

- `openclaw:local-sandboxed`: build completo, `docker-ce-cli` e
  `docker-compose-plugin` instalados via repo APT oficial (GPG
  verificado). 880MB final (+118MB sobre a imagem sem CLI).
- `openclaw-sandbox:bookworm-slim`: **cache hit total** — a imagem já
  existente localmente (6 semanas) já batia exatamente com o
  Dockerfile atual, sem drift.

Transferência pro Contabo:

```bash
docker save openclaw:local-sandboxed openclaw-sandbox:bookworm-slim | gzip | ssh contabo "gunzip | docker load"
```

Ambas confirmadas carregadas no Contabo (`docker images`).

## 6. Recriação e incidente

```bash
ssh contabo "cd /root/openclaw && docker compose up -d"
```

O `docker compose up -d` recriou os dois containers, mas o gateway
entrou em **crash loop** (exit 78, ~4 minutos):

```
read failed: Error: EACCES: permission denied, open '/home/node/.openclaw/openclaw.json'
Config file is not readable by the current process. If running in a container
or 1-click deployment, fix ownership with:
  chown 1000 "/home/node/.openclaw/openclaw.json"
```

**Causa raiz**: durante a etapa de aplicação dos arquivos, um `scp` do
`openclaw.json` preparado localmente deixou o arquivo no Contabo com
dono `1000:1000` (correto — é o que o processo do gateway, uid 1000
`node`, precisa). Isso foi identificado erroneamente como uma
regressão e "corrigido" de volta pra `root:root` — decisão baseada
numa suposição falsa: o arquivo de **backup** mostrava `root:root`,
mas isso era só um artefato do `cp` (sem `-p`) rodado como root, que
não preserva o dono original do arquivo copiado. O `openclaw.json` de
produção real sempre precisou ser uid 1000.

**Correção**:
```bash
ssh contabo "chown 1000:1000 /root/.openclaw/openclaw.json"
ssh contabo "docker restart openclaw-openclaw-gateway-1"
ssh contabo "docker restart openclaw-openclaw-cli-1"  # também tinha ficado unhealthy, só por tentar conectar durante o crash loop do gateway
```

Ambos os containers `healthy` em seguida. Sem impacto residual —
nenhuma mensagem de usuário foi perdida (o incidente ocorreu durante a
janela de manutenção, antes do teste funcional).

## 7. Validação completa

1. **`docker ps`**: `openclaw-openclaw-gateway-1` e
   `openclaw-openclaw-cli-1` ambos `healthy`, sem restart loop.
2. **Docker CLI no gateway**: `docker exec ... docker --version` →
   `Docker version 29.7.1, build e9452d6`.
3. **Grupo 988**: `docker exec ... id` →
   `uid=1000(node) gid=1000(node) groups=1000(node),988`.
4. **Teste funcional (parcial — ver ressalva abaixo)**: mensagem de
   teste via WhatsApp disparada pelo Max gerou um container real
   `openclaw-sbx-agent-main-f331f052` (imagem
   `openclaw-sandbox:bookworm-slim`, `sleep infinity`, criado ~1min
   antes da checagem — bate com a janela da mensagem), e os logs do
   gateway confirmam a tool policy do sandbox sendo aplicada:
   ```
   tool policy removed 3 tool(s) via sandbox tools.deny: cron, gateway, nodes
   tool policy removed 14 tool(s) via sandbox tools.allow: agents_list, ask_max, ...
   ```
   Isso confirma que o isolamento está configurado e sendo avaliado por
   turno — **mas é evidência indireta** (container existe, política é
   aplicada), não uma execução de tool bem-sucedida observada
   diretamente. Ver ressalva de 2026-08-05 11:39 UTC abaixo — a
   reexaminação mais rigorosa desse mesmo lote de logs achou só
   tentativas de tool **falhas**, não uma execução completa e
   confirmada.
5. **Zero erros novos pós-fix** — logs dos últimos 10min limpos,
   excluindo especificamente as linhas do crash loop já diagnosticado.

## Ressalva — 2026-08-05 11:39 UTC: execução real de tool dentro do sandbox NÃO comprovada diretamente

✅ RESOLVIDO — ver seção "Validação final do P0.2" mais abaixo.

Pedido do Max: reconfirmar, olhando os logs, se uma mensagem "recém
enviada" tinha disparado tool dentro de um `openclaw-sbx-*`. Comandos
rodados:

```bash
ssh contabo "docker logs openclaw-openclaw-gateway-1 --since 10m | grep -iE 'sandbox|openclaw-sbx|tool_executed'"
ssh contabo "docker ps -a --filter name=openclaw-sbx --format '{{.Names}} {{.Status}}'"
```

**Achado 1 — nenhuma atividade nova.** Hora do servidor no momento da
checagem: `2026-08-05T11:39:21 UTC`. A última linha de log do gateway
é de `11:30:42 UTC` — 9 minutos parado. Ou seja, a mensagem "que o Max
acabou de mandar" **não gerou nenhum evento novo no gateway** dentro
da janela verificada. O que apareceu no grep é o mesmo lote de teste
já coberto na seção 7 acima (item 4), não uma mensagem nova.

**Achado 2 — reexaminando esse mesmo lote sem filtro (`docker logs
--since 10m` sem grep)**, aparecem 7 linhas `WhatsApp Cloud reply
started for 554184445755` entre `11:29:28` e `11:30:34` (rajada de
mensagens em ~66s, não uma mensagem isolada) e 3 pares de "tool policy
removed" (resolução de política por turno, não execução em si). A
**única linha que representa uma tool efetivamente despachada** nesse
lote inteiro é:

```
2026-08-05T11:30:27.723+00:00 [tools] read failed: Sandbox FS error (ENOENT): MEMORY.md
2026-08-05T11:30:27.754+00:00 [tools] read failed: stat failed for /workspace/memory/2026-08-05.md: openclaw-sandbox-fs: 2: cd: can't cd to /workspace/memory
```

Isso é uma tool `read` roteada pelo shim de filesystem do sandbox
(`openclaw-sandbox-fs`), mas ela **falhou** (`ENOENT`, `cd` sem
sucesso) — comportamento esperado dado `workspaceAccess: "none"`
bloqueando acesso ao host, mas **não é uma execução bem-sucedida que
sirva como prova positiva** de "tool rodou dentro do sandbox e
funcionou".

**Conclusão honesta:** o funcionamento geral do sandbox está
confirmado (container `openclaw-sbx-*` sobe, imagem correta, Docker
CLI presente, grupo 988 presente, tool policy sendo resolvida por
turno). **A execução real e bem-sucedida de uma tool dentro do
container ainda não foi exercitada/comprovada de forma direta** — as
únicas tentativas de tool observadas nos logs até agora falharam (por
design, `workspaceAccess: none`) ou não deixaram rastro claro de
sucesso. Fica como pendência: mandar uma mensagem que force uma tool
permitida (ex.: `web_search`, ou algo que precise de `exec` se
habilitado) e confirmar nos logs um `tool_executed`/resultado
bem-sucedido correlacionado a um `docker exec` real dentro do
`openclaw-sbx-*`.
